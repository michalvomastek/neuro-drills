# Neuro drills – notes for Claude

Godot 4.7 project: a collection of short cognitive-training mini games ("drills").
Plan, architecture, roadmap and open decisions live in `docs/PLAN.md`. Read it first and keep it current. `docs/DRILLS.md` lists every drill with its settings, `docs/OVERVIEW.md` is the maintainer-facing table (how it works, what it trains, why); add a row for every new drill.

## Working with the maintainer

- The maintainer writes in Czech. Reply in Czech. Code, identifiers, comments, commit messages and this file are in English.
- UI strings: Czech and English, keys in `assets/translations/ui.csv`, Czech is the default locale. Every user-facing text goes through a key (scene `text` properties auto-translate; code uses `tr()`).
- Work on the assigned `claude/*` branch. Do not open pull requests unless asked.
- **Never push to `main` unless the maintainer's current message explicitly asks for it** ("pushni na main" / "přesuň na main"); an earlier approval does not carry over to the next change. Every push to `main` deploys to Pages and burns GitHub Actions minutes (maintainer's request, 2026-10-07, after two unasked pushes).
- Commit messages carry no attribution trailers: no `Co-Authored-By`, no `Claude-Session` lines (maintainer's request, 2026-10-03).
- Instructions that name a mouse, the space bar or arrow keys have a `<KEY>_TOUCH` twin in `ui.csv`; `Drill.describe(key)` picks it on a touchscreen (menu, setup panel, training brief). Add the twin whenever a new text mentions a peripheral.
- Headless Godot cannot judge UX. Render changed scenes with `tools/godot.sh screenshot` and look at the PNG before claiming a UI change works; the maintainer does the final check in the editor.

## Engine and environments

- Godot 4.7-stable (`4.7.stable.official`), GDScript only, renderer GL Compatibility (web and mobile friendly). Do not change the renderer, `config/features` or the warning levels in `project.godot` without asking.
- Maintainer's machine (Windows): this repository, the Godot editor and a clone of godot-docs are sibling folders under `C:\Agile Fitness Coach App\`: `..\godot\` holds the editor binary, `..\godot-docs\` the manual sources.
- Cloud sessions: no Godot binary, no display, and godotengine.org / docs.godotengine.org are blocked, while GitHub release downloads work. `tools/godot.sh` downloads 4.7-stable into `~/.cache/neuro-drills/` on first use. Xvfb and Mesa (llvmpipe) are available, so software rendering works.

## tools/godot.sh

| command | what it does |
|---|---|
| `version` | resolve the binary (`$GODOT_BIN`, then `../godot/`, then cached download) and print the version |
| `import` | headless import; catches broken scenes and resources |
| `check [files]` | import, then load every `.gd` file (or the given ones) inside a running project via `tools/check_scripts.gd`; parse, analyzer and compile errors fail it, including warnings configured as errors and unknown autoload names (`--check-only` cannot see autoloads, so it is not used) |
| `test` | run `tests/run_tests.gd` headless: every `tests/test_*.gd` extending `TestCase`, methods prefixed `test_` |
| `docs` | dump the engine class reference XML to `~/.cache/neuro-drills/apidocs/`; grep it instead of guessing an API |
| `playthrough` | play every registered drill to the end with random input under Xvfb (`tools/playthrough_drills.gd`, `PLAYTHROUGH_ONLY=id,id` limits it) and check metrics, summary rows, history record and benchmark; finds crashes in the trial loop and `build_result` that `smoke` cannot; runs against a throw-away data directory and sets the user files aside, so it never touches the player's history |
| `smoke` | start every registered drill with the countdown on under Xvfb and verify it is running (`tools/smoke_drills.gd`); catches start-up regressions the logic tests cannot |
| `screenshot <scene> <out.png> [WxH] [frames]` | render a scene with software OpenGL (Xvfb when there is no display) and save a PNG; `SCREENSHOT_LOCALE=cs` picks the language |
| `theme` | build `ui/theme/dark_theme.tres` and `light_theme.tres` from the palettes in `tools/make_theme.gd`; never edit the `.tres` by hand |
| `icons` | render `icon.svg` into `assets/icon/icon_{144,180,512}.png` for the web manifest and the boot splash (`tools/make_icons.gd`) |
| `templates` | download and install the 4.7 export templates (about 1 GB, GitHub release) |
| `export <preset> [out]` | release export with a preset from `export_presets.cfg` (`Web`, `Windows Desktop`); output defaults to the preset's `export_path` under `build/` (ignored by git) |
| `exec [args]` | pass arbitrary arguments to the binary |

Run `import`, `check`, `test` and `smoke` before every commit, `playthrough` after touching a drill's trial loop or result. `check` is also the fastest way to find out whether an API or a member exists in 4.7.

## Architecture in one paragraph

`ui/app/app.tscn` is the main scene: a fixed two-row top bar (the level inside an `XpRing` (`ui/common/`), streak, daily-goal and badge chips (coloured disc with an icon, plain number; the badge chip opens the profile) with the quit icon button (desktop only) on the first row, the screen title and a back arrow on screens without a tab on the second), the host of the current screen and a fixed bottom bar with five tabs (drills, training, progress, profile, settings; SVG icons in `assets/icons/`, white strokes tinted by the theme's icon colours). It attaches the host to the `SceneRouter` autoload, which swaps one screen at a time and emits `screen_changed(id)`; the bars show for the ids the shell knows (menu, training, progress, profile, settings, feedback) and for `SceneRouter.DRILL_SETUP` (a drill's setup panel: the title is the drill's name, the back arrow calls `SceneRouter.abort_drill()`; `Drill.phase_changed` tells the router when the panel shows or a run starts), while a running drill, the results, a training brief or the onboarding take the whole window. Setup panels therefore carry no title and no Back button of their own: a flat `Screen` column (560 units, Schulte 640) with the screen margins and a full-width Start. `DrillRegistry` (autoload) lists `DrillDefinition`s. A drill scene extends `Drill` (`core/drill.gd`), receives `setup(definition, config, autostart)` after entering the tree and reports through `finished(result)` / `aborted`. `DrillResult` carries time, errors, config, `summary_rows` for the shared `ResultsScreen` and standardised `metrics` (String -> float) that `core/benchmarks.gd` turns into an indicative level (beginner / advanced / elite, see `docs/BENCHMARKS.md`); every `build_result` must fill `metrics`. `StatsStore` (autoload) appends each result as one JSON line to `user://results.jsonl` through `StatsHistory` (`core/stats_history.gd`, pure logic: trend vs the last 10 runs of the same variant, personal best, overview per variant) and `MetricCatalog` (`core/metric_catalog.gd`: primary metric and direction per drill, variant key from the config, variability and fatigue index from the per-trial times). The results screen shows the trend, record, variability, fatigue and an optional RPE row (1-10); `ui/progress/` is the progress screen with a `Sparkline`. Training: `TrainingPlan` (`core/training_plan.gd`, duration estimates, suggestion by weakest category, saved plans JSON) and `TrainingSession`; `SceneRouter.training` is non-null while a training runs, every step opens with `TrainingBrief` (`ui/training/`, drill, variant, description, help, Start), the results screen then advances with `continue_training()` and the run ends on `TrainingSummary`. Feedback notes (`FeedbackLog`, `core/feedback_log.gd`; persisted by `StatsStore` in `user://feedback.jsonl`) are written from the results screen (`NoteDialog`, result and environment attached) or on the feedback screen (`ui/feedback/`, reached from Settings), which copies or downloads them as plain text for the chat; "Send to GitHub" opens a prefilled new-issue page (label `feedback`) in `FeedbackLog.ISSUE_REPO`, so collected feedback lives in the repository's issues. Schulte: `schulte_logic.gd` (rules, testable), `schulte_config.gd` (settings <-> Dictionary), `schulte_table.gd` (scene). Trial-based drills (reaction time, choice reaction, Go/No-Go, Stroop, Flanker) extend `TrialDrill` (`core/trial_drill.gd`), which builds the setup panel, play frame, countdown and cancellable `_wait()`; each has a `*_logic.gd` class and a three-line `.tscn`. `ReactionStats` summarises reaction times. The results screen shows only `summary_rows`, so every drill adds its own rows. Theme: two generated resources (`ui/theme/dark_theme.tres`, `light_theme.tres`, built by `tools/make_theme.gd` from one palette each; fonts Nunito for text and Baloo 2 for headings in `assets/fonts/`, OFL, both subset to Latin with Czech (about 100 kB each; `pyftsubset` from fonttools, keep the weight axis), with `symbols.ttf`, a DejaVu Sans subset, as fallback for arrows, shapes, box drawing and check marks: the web export has no system fonts, so a glyph outside these three files renders as a box on iOS). `App.apply_theme` loads the one named by `StatsStore.theme_name` onto the main scene and paints the clear colour; a `Window` inherits it. Type variations: `PrimaryButton`, `DangerButton` (destructive, red), `CardButton`, `DimLabel`, `PillLabel`, the type scale `TitleLabel` (30, screen title in the top bar and on full-window screens: results, summary, brief, onboarding), `HeadingLabel` (24, section heading: menu category, "Badges 7/12", progress variant), `ItemLabel` (20, item title: drill card, profile row, badge name), body 20 and `NoteLabel` (16, dim secondary text: descriptions, details); never override a label's font size, pick the variation, `Card`, `Sunken`, `Pill`, `GoalPill` (onboarding dots), `BadgePill` / `BadgeOffPill`, `Screen` (the panel of a top-level screen: no card, the content sits on the background between the bars), `NavBar` / `TopBar` / `BottomBar` / `FilterBar` (the menu's pinned category strip), `NavButton` (flat tab, icon above label, active in `primary`), `IconButton`, `SchulteCell`, `Pad` (colours `go`, `correct`, `wrong`, `wrong_dim`), `Board` (colours `cell`, `lit`, `selected`, `occluder`, `ink`, `line`, `task_*`) and `App` colours (`bg`, `primary`, `accent`, `green`, `orange`, `red`, `yellow`, `on_yellow`, `level_*`). Code never hard-codes a colour that must work on both backgrounds: drawn shapes read `Board/ink`. Sounds: autoload `Sfx` synthesises its tones at start-up (`Sfx.play("correct"|"wrong"|"done"|"tick"|"tone"|"high"|"low")`; feedback tones obey `StatsStore.sound_enabled`, stimulus tones always play). `ui/profile/` shows the gamification numbers and every badge (`GamiWidgets` builds the pills for the menu and the profile and the badge medallions, coloured SVGs in `assets/badges/<id>.svg` imported at double scale with mipmaps, faded when locked); `ui/onboarding/` is the three-page first start (`StatsStore.onboarding_done`, skipped for a player with history) ending in `SceneRouter.start_suggested_training(5)`. Settings live on `ui/settings/` (locale, theme, `Layout.text_scale`, sounds, RPE), persisted by `StatsStore` in `user://settings.cfg`. Setup panels show `MetricCatalog.help_text` (what the drill measures and the band bounds). Gamification (`core/gamification.gd`, pure logic): XP per record, level thresholds, streak and daily goal in local days (`tz_bias_min`; the goal is a fixed `DAILY_GOAL_MINUTES` = 5, independent of the training length), badges derived from the records; `StatsStore` exposes `current_streak`, `minutes_today`, `level_info`, `earned_badges`, `take_new_badges`.

## Code conventions (GDScript)

- Static typing everywhere: variables, parameters, return types, typed arrays. `project.godot` turns untyped declarations, unsafe method/property access, unsafe call arguments and unused variables into errors, so `check` enforces this. Use `:=` for inference and `as` for downcasts. Dictionary values are `Variant`: assign them to a typed variable first (`var n: int = dict["n"]`), do not pass them straight into `int()`/`bool()` or typed parameters.
- A button in `ACTION_MODE_BUTTON_PRESS` receives both the touch event and the mouse event emulated from it and fires `pressed` twice per tap (release mode dedupes). Create press-triggered buttons with `Drill.make_press_button()`, which swallows the touch events; never set the action mode directly.
- Lists scroll by dragging through `DragScroll` (`core/drag_scroll.gd`), which the app shell attaches to every `ScrollContainer` (`node_added`): the engine's own touch scrolling needs a touchscreen the display server reports and a press that reaches the container, and a button in the list swallows it, so on an iPhone in the browser lists moved only through the scrollbar. A drag beyond the deadzone sends `NOTIFICATION_SCROLL_BEGIN` so the pressed button lets go. On a touchscreen (`DragScroll.touch_ui()`, forced headless with `NEURO_TOUCH_UI=1`) the permanent scrollbar is hidden and a thin indicator fades in while the content moves. The menu filters its categories with a horizontal strip of pills (first pill "All") on every screen size; the tab bar's arrows were the only way to page. Long drop-downs (drills, plans, progress variants) are `ListPickButton` (`ui/common/`), a button opening a PopupPanel with a scrollable list of buttons: the engine's PopupMenu picks the item under the finger when a drag ends, so `DragScroll` leaves PopupMenus alone and short menus keep the OptionButton.
- Mouse motion events do not reliably reach `_unhandled_input` under Controls; read the pointer per frame instead (`get_local_mouse_position()`), parking it with `Input.warp_mouse()` when relative movement is needed (compensatory tracking).
- A script started with `-s` (test runner, tools) is compiled before autoloads exist, so it must reach them through `root.get_node("SceneRouter")` and `call()`; ordinary scene scripts use the autoload names directly.
- A logic method that advances state must do so even on a wrong answer; a test looping `while not is_done()` hangs forever otherwise (seen once when a dependency failed to load). Run tests with a timeout when in doubt.
- Every drill that extends `TrialDrill` must clear its own flags, timers and highlights in `_reset_play_state()`; it runs on Back, on Start, on completion and once from `_ready()` before `_on_setup()`, so it must only touch nodes built in `_build_play_area()` or null-check them. `_wait()` only checks the run token, never `_running` (the countdown waits before `_running` is set).
- The test runner cannot detect runtime errors inside a test (GDScript has no exceptions); read the `SCRIPT ERROR` lines in the test output, and keep `check` green first.
- Naming: files and folders `snake_case`; classes `PascalCase`, with `class_name` only for shared types; constants `UPPER_SNAKE_CASE`; private members prefixed with `_`; signals in past tense (`drill_finished`).
- One folder per drill under `drills/<drill_id>/`: scene, scene script, a pure-logic class (RefCounted, no Node access, takes a `RandomNumberGenerator` or a seed) and its tests. Scene code only translates input into logic calls and renders state.
- UI: Control nodes and containers only; no hard-coded pixel positions or sizes; shared theme; mouse and touch both work. `Layout` (`core/layout.gd`) scales the window so the shorter side is 720 units in landscape and 480 in portrait; a centred panel takes its width from `Layout.panel_width()` and a screen that needs a one-column phone layout registers `_relayout()` through `Layout.watch()` and asks `Layout.is_narrow()`. A container that flips direction must be a plain `BoxContainer` (`vertical` is locked on HBox/VBox). A centred panel sits inside a `ScrollContainer` (results, TrialDrill and Schulte setup), because a phone browser with its bars shows only about 430x660 CSS px. A wrapping `Label` inside a `Window` needs its width before the window enters the tree, or the window grows past the screen (`NoteDialog` takes the screen size in `_init`). Text input on the web needs `html/experimental_virtual_keyboard=true` in the preset, otherwise no keyboard appears on phones. Render changed screens at 1280x720, 412x915 and 430x660.
- Timing: `Time.get_ticks_msec()` / `Time.get_ticks_usec()` for measurements, never accumulated `delta`.
- Autoloads only for app-wide state (see PLAN.md); anything a scene can own, it owns.
- Persisted numbers go through JSON, which has no NaN: store a missing number as `null` (`StatsHistory._or_null`) and read it back with `StatsHistory.number()`. Ints come back as floats, so compare config values through `MetricCatalog._value_text()` or typed variables, never with `==` against an int literal after a round trip.
- `.tscn` and `.tres` files are text: keep diffs minimal, never reformat, let the editor own UIDs. `.godot/` stays untracked.
- Commit messages: `type(scope): summary`, e.g. `feat(schulte): add grid generation`; types feat, fix, refactor, test, docs, chore.
